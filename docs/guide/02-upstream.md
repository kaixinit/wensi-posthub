# 上游 API 接入

## 文思量化等上游如何填写

在“上游分发”点击“创建上游接口”，填写上游名称，复制平台生成的完整接入地址。接口地址已包含独立密钥。上游主动向文思邮差提交消息，无需文思邮差反向登录上游。

日常配置集中在“已接入上游”每一行：“接入配置”查看地址与消息格式，“下游配置”选择下游渠道，“停用密钥”暂停新推送，停用后可以删除。

## 每个上游独立配置下游

在该上游的“下游配置”中添加或勾选已验证渠道，设置自己的收件确认选项并保存。修改 A 上游的渠道、确认要求或等待时间，不会更改 B 上游的配置。上游不再引用共享分发方案。

同一渠道可以被不同上游分别授权，各上游的勾选独立保存。下游渠道负责维护连接本身；不要把停用或删除渠道连接与取消某个上游的勾选混淆。

从旧版升级时，原默认方案的实际收件渠道和确认设置转存到对应上游，解除共享引用；原授权范围内未被旧方案选择的渠道不会自动加入。旧方案缺失或包含未授权渠道时，暂停该上游的新分发，提示核对下游并保存。已排队消息、密钥和历史记录保留。

## 上游请求参数

| 配置项 | 填写方式 |
| --- | --- |
| URL / Webhook | 平台生成的完整接入地址，已包含密钥 |
| 请求方式 | POST |
| 内容类型 | application/json |
| 独立密钥 / Authorization | 使用完整接入地址时留空 |
| 消息格式 | 下方 JSON；先用固定文字测试，再替换成上游支持的变量 |

```json
{
  "title": "文思量化测试通知",
  "body": "这是一条连接测试消息，请确认收到。",
  "request_id": "wensi-test-001"
}
```

**地址示意，不能原样提交：** `https://你的域名:端口/api/v1/hooks/ph_实际密钥`。打开“接入配置”可以根据当前访问网址生成示例；密钥需使用创建时保存的真实值。

专属地址只要求 `body` 必填；省略标题时使用“上游通知”。每条新业务消息使用新的 `request_id`，同一事件超时重试保持原编号和原内容。省略编号会自动生成，但重复提交可能产生重复通知。

## 标准 API

支持请求头的程序也可使用 `POST /api/v1/messages`，请求头为 `Authorization: Bearer 实际密钥`。此入口的 `title`、`body`、`request_id` 必填；省略目的地时，按本上游独立的下游配置发送。也可用 `target_ids` 指定本次收件渠道，但必须属于当前上游已授权的范围。

标准 API 和专属接入地址都使用当前上游自己的渠道与收件确认设置。上游请求不再支持 `profile_id`，传入时会明确拒绝；请移除此字段，或改用已授权的 `target_ids`。管理员系统分发仍可使用手动发送方案，其修改不会影响上游。

## 返回值与密钥

| 结果 | 含义 / 处理 |
| --- | --- |
| HTTP 202 | 已接收并保存，仍须查看实际投递结果 |
| `routing_state=awaiting_routing` | 下游尚未配置，消息已保存，暂未发送 |
| `routing_state=routed` | 已安排投递，不代表渠道已接受或收件人已读 |
| 401 / 403 | 检查密钥、应用启用状态和目的地授权 |
| 409 | 核对返回原因，可能是业务编号与内容冲突，或下游配置需核对；同一事件重试保持编号和内容一致 |
| 422 | 检查必填字段、JSON 格式和时间是否带时区 |

使用响应中的消息编号，可在“投递记录”查看详情；程序也可携带 Bearer 密钥查询 `GET /api/v1/messages/{id}`。

接入密钥**没有自动到期时间，也不会发送一次就失效**。停用后暂停新请求，重新启用可恢复。重置后旧密钥及旧专属地址立即失效，需更新上游配置。密钥明文无法从后台找回。

完整接入地址含有凭据，请勿公开分享。文档示例不会读取或展示实际密钥。
