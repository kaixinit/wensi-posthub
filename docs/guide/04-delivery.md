# 分发、时间与回执

## 手动发送消息

打开“系统分发”，填写标题和正文，勾选已验证的渠道，也可从已有分发方案带入渠道。发送时间留空立即安排，填写时间则预约发送。点击“提交分发”后，在“投递记录”查看每个渠道的结果。

## 应用之间如何隔离

“上游分发 → 下游配置”中勾选的渠道，只允许这个应用使用。其他应用不会自动获得授权；同一渠道如果被两个应用分别勾选，会接收这两个应用的消息。

每个上游独立保存渠道列表、是否要求收件确认及等待时间。没有指定本次渠道时，按本上游的渠道列表分发。修改一个上游不会改变其他上游的选择；上游不再使用共享分发方案。

修改配置后，后续新消息按新配置发送；已经入队的消息保留提交时的目的地。已保存的“待配置分发”消息需要单条确认放行，不会因添加渠道而自动补发所有历史消息。

## 收到后是否立即发送

未设置发送时间时，消息保存后进入后台队列，尽快发送。正常空闲时通常很快开始，但网络、渠道限速、队列和重试会影响耗时，不承诺固定秒数。

| 时间 | 用途 |
| --- | --- |
| 创建时间 | 中转台接收并保存消息的时间 |
| 计划发送时间 | 留空立即安排；填入时间则预约发送 |
| 投递截止时间 | 到期停止待发送和重试，默认计划发送后 24 小时；与密钥有效期无关 |
| 确认等待时间 | 要求收件人确认时，超过此时间仍未确认会告警 |

页面时间按当前浏览器时区填写。API 时间必须包含时区，例如 `2026-12-01T09:00:00+08:00`；这是格式示例，应替换成需要的未来时间。

## 如何判断投递结果

| 页面状态 | 含义 / 下一步 |
| --- | --- |
| 待配置分发 | 已保存但没有下游，先配置应用再确认分发 |
| 等待发送 / 正在发送 | 队列处理中，稍后刷新 |
| 等待重试 | 连接失败或限流后自动重试，详情显示下次尝试时间；持续至成功或投递截止 |
| 等待微信会话 | 微信返回 `ret=-2 / prepare failed` 且没有成功消息编号；请在收件微信中向机器人发一句话，平台收到新会话后自动续发未过期消息 |
| 渠道已接受 | 发送接口返回成功回执，不代表实际已读 |
| 收件人已确认 | 收件人完成确认操作，或管理员根据明确收件反馈登记；详情保留确认依据 |
| 发送失败 / 投递受阻 | 查看详情及错误原因，修复配置后重试 |
| 结果待核实 | 可能已送达；先询问收件人；确认已收到后点击“核实已收到”，避免重复发送 |
| 已过期 / 已取消 | 对应任务不再继续发送 |

一条消息发往多个目标时，每个目标独立记录结果。部分失败不会使成功的目标自动重发。

微信“等待会话”与代理断线的定时重试不同：等待期间不会反复使用旧会话发送，也无需重新绑定或手动重发。后台只接受原收件人的新会话，更新后自动安排该渠道的未过期任务；重启保留等待状态，取消或删除后不会恢复发送。已停用或未验证的渠道不会自动投递，重新绑定、更换配置需重新检查任务。投递截止后停止；收件验证码还受自身十分钟有效期限制，已被新验证码替换的旧码不会再发送。

`prepare failed` 的原因由微信服务端决定，不能仅凭这个返回码断定具体原因。新会话后若仍被拒绝，会继续显示等待并保留告警；授权失效需扫码修复。其他未识别错误仍记录失败，响应矛盾或网络回执不明保留“结果待核实”，不会直接标成成功，也不会自动重发。旧版本没有保留具体原因的历史失败记录不会在升级时批量补发。

“核实已收到”仅用于确实得到收件人反馈的记录。登记后清除当前异常提示，保留原始发送结果、确认时间和操作记录，并处理对应告警；不会再次发送消息。尚未核实的记录不要直接登记成功。

“告警中心”可查看异常并标记处理。“等待重试”的任务会自动继续，不需要手动操作。标记已处理不等于重新发送；永久失败、配置受阻或结果不明时，需先核实原因，再按详情处理。可在网络通信中指定已验证渠道作为告警出口。
